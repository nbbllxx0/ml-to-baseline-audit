# Strong classical baseline — pre-registration

**Version:** 1.0 · **Written:** 2026-09-24 · Frozen in `evidence/MANIFEST.sha256` before the first timing run.
Deviations go in §9.

**Purpose.** Supply the "efficient classical method" that rule R2 and the re-tests (C2, C3) need.
- The baseline changes **how** the state equation is solved.
- It does **not** change **what** is optimized: formulation, filter, penalty and update stay those of the target
  article (or of top88 when no target applies).

This separates implementation efficiency from algorithmic tuning (risk R3 in the scan report).

---

## 1. Formulation (standard modified SIMP, 2D plane stress)

- **Mesh.** nelx × nely unit-square 4-node bilinear elements, 2×2 Gauss quadrature.
- **Material.** E₀ = 1, E_min = 1e-9, ν = 0.3, E(ρ) = E_min + ρᵖ(E₀ − E_min), p = 3 constant. No continuation unless a
  target's generator uses it.
- **Filter.** Density filter with cone weights w = max(0, r_min − d), normalised by the row sum; this is top88
  `ft = 2`. The CPU path uses a sparse H. The GPU path uses the same weights as a convolution. The two are
  mathematically identical.
- **Update.** Optimality criteria: move 0.2, damping 0.5. Bisection on the physical-volume constraint until
  (l₂ − l₁)/(l₁ + l₂) < 1e-3.
- **Initial design and objective.** x = volfrac everywhere. Compliance c = fᵀu.
- **Sensitivities.** dc = −p ρᵖ⁻¹ (E₀ − E_min) u_eᵀ K_e u_e; dv = 1. Both are filtered by Hᵀ, as in top88.

## 2. Problems for the provisional G2

| ID | Domain | Supports | Load | volfrac | r_min |
|---|---|---|---|---|---|
| P1 | cantilever, n × n | left edge clamped | unit downward force at the right-edge mid-node | 0.4 | 1.5 × n/64 |
| P2 | MBB half-beam, n × n | left edge u_x = 0; bottom-right node u_y = 0 | unit downward force at the top-left node | 0.5 | 1.5 × n/64 |

n ∈ {64, 256}. r_min scales with n, which keeps the physical length scale constant (1.5 at 64, 6.0 at 256).

The final G2 and all re-tests replace P1 and P2 with the target article's own problem definitions and generator
settings, recorded in §9.

## 3. Solvers

| ID | Role | Method | Environment |
|---|---|---|---|
| **S-GPU** | strong | Matrix-free Galerkin geometric-multigrid–preconditioned conjugate gradient (PCG), float64, on the GPU | conda `torch5090`: Python 3.12.13, torch 2.11.0+cu128, CUDA 12.8, RTX 5090 (sm_120) |
| **S-PARDISO** | strong CPU | Sparse assembly in scipy CSR, reduced to free DOFs, solved by MKL PARDISO through `pypardiso` | conda `Pytorch`: Python 3.10.18, scipy 1.15.3, pypardiso 0.4.7 |
| **S-SuperLU** | reference ("typical Python port") | Same assembly, `scipy.sparse.linalg.spsolve` (SuperLU) | conda `torch5090`: scipy 1.17.1 |

**S-GPU details.**
- **Fine operator.** Matrix-free: gather u_e, apply E_e K_e, scatter-add.
- **Levels.** Coarsen by 2 while both element counts are even and the smaller exceeds 8. That gives 256 → … → 8 (6
  levels) and 64 → … → 8 (4 levels).
- **Coarse operators.** Element-local Galerkin: coarse K_c = Σ over the 4 children of P̃_kᵀ K_child P̃_k.
  - P_k is the bilinear interpolation from the parent element's 8 DOFs to child k's 8 DOFs.
  - P̃_k masks fixed DOFs on both sides. Coarse fixed DOFs are coarse nodes coincident with fixed fine nodes.
  - This equals the global Galerkin product P̃ᵀKP̃. It is recomputed every design iteration and is included in the
    timing.
- **Smoother.** Damped Jacobi.
  - Start with ω = 0.6, V(2,2).
  - **Selection rule, fixed now:** if any PCG solve on P1 at n = 64 (iterations 1–150) does not reach tolerance within
    200 PCG iterations, try V(3,3) with ω = 0.5. The first configuration that passes is frozen for every problem and
    recorded in §9.
- **Coarsest level.** Assembled dense matrix with identity rows for fixed DOFs, solved by Cholesky.
- **Convergence.** Stop when ‖r_k‖/‖f‖ ≤ 1e-8 by the CG recurrence. Then recompute the **true** residual ‖f − Ku‖/‖f‖.
  Accept only if it is ≤ 1e-7; otherwise keep iterating, up to 500. Every solve's true residual is logged; this is the
  W20 admissibility principle.
- **Warm start** from the previous design iteration's u.

**Equivalence requirement.** On P1 and P2 at n = 64 and n = 256, after 150 iterations, S-GPU, S-PARDISO and S-SuperLU
must agree: relative difference in final compliance ≤ 1e-5, and max |Δρ_phys| ≤ 1e-3. If they disagree, stop and
diagnose before any timing is reported.

## 4. Timing protocol

- **Fixed 150 design iterations.** This matches OAT's Table 6 protocol ("150 steps of optimization (average needed to
  converge)"). The first iteration at which ‖Δx‖∞ < 0.01 is also recorded, for information.
- **Warm-up.** One 10-iteration run per solver and problem size, discarded.
- **Repeats.** Three timed repeats; report the median, minimum and maximum.
- **Timed region.** The whole design loop: filter, assembly (CPU paths), coarse-operator build (S-GPU), solve,
  sensitivities, OC, compliance.
  - Excluded: one-time setup (index arrays, K_e, hierarchy index maps). Setup is reported separately.
  - GPU timers use `torch.cuda.synchronize()`.
- **Per-iteration log.** Compliance, physical volume, change, solve time, PCG iterations, true residual.

## 5. Energy protocol

- `nvidia-smi --query-gpu=timestamp,power.draw,clocks.sm,utilization.gpu --format=csv -lms 100` runs during the timed
  region.
- A 5 s idle trace is taken first.
- Report both GPU board energy (trapezoidal integral) and energy above idle.
- CPU package energy is **not** measured on this Windows machine; this is a stated limitation.

## 6. Hardware and software record

`tools/envcapture.py` writes `env/<date>_env.json` before the runs. It records GPU (model, memory, driver), CPU
(i5-14600KF, 14 cores / 20 threads), RAM (95.8 GiB), OS, and Python and library versions per conda env.

OAT's Table 6 used an RTX 4090 and an i9-14900K. Our numbers are never mixed with theirs in one comparison; published
numbers appear separately and labelled.

## 7. Matched-quality protocol (re-tests; completed when target code is available)

Time-to-quality compares the classical trajectory with the ML output under **the target article's own compliance
evaluation**. The same thresholding and post-processing are applied to both. The exact procedure is recorded in §9
before any re-test run.

## 8. Outputs

- `retest/runs/<run_id>/record.json`: configuration, environment hash, per-iteration arrays, timings, residuals.
- `power.csv` and `design.npz` (final physical density) in the same run folder.
- `evidence/baseline_tests.json`: equivalence and unit-test results.
